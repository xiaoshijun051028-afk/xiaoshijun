# ADR-004 · 存档格式：版本化 JSON + 原子写盘

> 编号 ADR-004 ｜ 日期 2026-08-08 ｜ 作者 程基岩 ｜ 评审 Solo
> 关联：`architecture.md` §10 ｜ 上游：GDD S8 `meta-progression.md`、S5 `world-level.md`、S3 `resonance.md`

## 状态

**已接受（Accepted）**

## 背景

GDD S8 规定神龛是**唯一存档/复活点**，需持久化：玩家状态、共鸣池、岛屿进度、残响收集、技能树。同时给出三条边界要求（S8 §⑥）：

- **写盘失败**：保留内存状态，提示"未保存"，**不崩溃**；
- **无神龛死亡**：兜底用中枢岛神龛；
- **读档版本不匹配**：**拒绝并提示，不损坏**。

第三条尤其关键：它明确要求存档带**版本概念**，且要求失败是"优雅拒绝"而非"读一半崩掉"。

还有一条隐含但更重要的约束来自 ADR-002：共鸣池是单一真相源。**如果存档写入 `MAX=100`、`FINISHER_COST=40` 这类规则常量，那么调平衡后老存档会把旧规则带回内存，制造第二真相源，直接破坏 P4 支柱的工程保障。**

### 备选方案

- **A. 版本化 JSON**（`JSON.stringify` / `JSON.parse`）
- **B. Godot `ConfigFile`**（ini 风格）
- **C. 二进制 `var_to_bytes` / `FileAccess.store_var`**
- **D. `ResourceSaver` 存 `.tres` / `.res`**
- **E. SQLite（GDExtension）**

## 决策

**采用 A：版本化 JSON，明文，配合原子写盘与校验和。**

### 1. 位置与文件

```text
user://saves/slot_1.json        # 主存档
user://saves/slot_1.json.bak    # 上一份成功存档（回退用）
user://saves/slot_1.json.tmp    # 写入中间态（正常情况下不应长期存在）
user://settings.json            # 画质/音量/可访问性 —— 独立
user://input_map.json           # 按键重映射 —— 独立
```

**设置与按键独立于存档**：换存档/删档不该丢按键配置与可访问性设置。对依赖可访问性设置的玩家，这是体验红线。

### 2. Schema（详见 `architecture.md` §10.2）

顶层必备三字段：

```jsonc
{
  "schema_version": 1,     // 整数，单调递增
  "game_version": "0.4.0", // 仅供诊断，不参与兼容判定
  "checksum": "sha256:…",  // 覆盖除自身外全部内容
  …
}
```

### 3. 只存"玩家造成的差异"，不存可推导数据

**入档**：共鸣池当前值、神龛 id、岛屿 id、玩家 transform、已解锁岛屿/已开闸门/已激活神龛/已触发节点、残响收集、技能点与已解锁技能、统计数据。

**绝不入档**：
- 任何 `GameConstants` 常量（`RESONANCE_MAX` / `GATE_COST` / `FINISHER_COST` / `CANCEL_WINDOW` …）——**这是 ADR-002 单一真相源的延伸保护**；
- HP / combo / hitstun / iframe（GDD S1 §③ 明确"不持久"，复活恒满血）；
- 任何可从上述数据推导的派生值。

### 4. 原子写盘

```text
写 .tmp → flush/close → 重新读回 .tmp 并校验 checksum
  ├ 校验通过 → 现有存档改名为 .bak → rename(.tmp → .json)   ← 原子
  └ 校验失败 → 删除 .tmp，保留原存档
                emit save_completed(false)
                HUD 提示"未保存"（GDD S8 §⑥）
```

`DirAccess.rename()` 在同一文件系统上是原子操作。断电/崩溃的最坏结果是丢失**本次**存档，绝不会产生半截损坏文件。

### 5. 读档与版本策略

```text
读 slot_1.json
├ 文件不存在        → 新游戏（共鸣池 = INITIAL 50）
├ JSON 解析失败      → 尝试 .bak；仍失败 → 提示"存档损坏"，不覆盖，不崩溃
├ checksum 不匹配    → 同上（提示可能被篡改/损坏）
├ schema_version > 当前 → 拒绝："存档来自更新版本"（GDD S8 §⑥）
├ schema_version < 当前 → 走迁移链 migrate_1_to_2() → … ；无迁移器则拒绝
└ 通过 → 反序列化 → 逐字段钳制（防篡改）→ 应用到 S1/S2/S3/S5/S7
```

**字段钳制是安全边界**：`resonance.current` 读入后必须 `clampi(v, 0, GameConstants.RESONANCE_MAX)`。明文 JSON 意味着玩家可以手改，我们不试图阻止（单机游戏，作弊是玩家自由），但**绝不允许非法值让游戏进入不一致状态或崩溃**。

### 6. 不做加密/防篡改

单机单人游戏，无排行榜（Steam 排行榜是 Could 级）。加密只会：增加复杂度、让玩家无法自救损坏存档、让我们自己调试变难。**若未来 Steam 排行榜（Could）落地，排行数据走 Steam 后端校验，不依赖本地存档可信度。**

## 后果

**正面**

- **可读可调试**：Solo 开发中，能直接用文本编辑器打开存档定位问题，价值极高。玩家报 bug 时可让其附上存档。
- **迁移友好**：JSON 加字段天然向后兼容（旧档缺字段用默认值）；配合 `schema_version` 与迁移链，长期演进成本低。这对"边做边改设计"的预制作阶段是刚需。
- **崩溃安全**：原子写 + `.bak` + checksum 三层，满足 GDD S8「写盘失败不崩溃」，并超出要求地提供了回退能力。
- **保护单一真相源**：常量不入档，从根上杜绝"老存档带回旧规则"。
- **测试简单**：存档模型是纯逻辑（`src/meta/save_model.gd`），序列化/反序列化/迁移/钳制全部可无场景单测，直接覆盖 GDD S8 §⑦ 四条验收标准。
- Godot 原生 `JSON` 类，零依赖。

**负面 / 成本**

- **明文可改**：玩家可自行修改进度。已判定为可接受（见决策 6）。
- **体积与解析速度**：JSON 比二进制大且慢。本项目存档规模极小（数十 KB 量级：几个字符串数组 + 十余个标量），60 fps 下一次存档解析远低于一帧，且存档只发生在神龛交互（有过场动画掩盖）。**非瓶颈**。
- `JSON.parse` 返回 `Variant`，需手工类型校验。已通过"逐字段钳制 + 显式类型转换"处理，且这层校验本来就是防篡改所必需的。
- 浮点精度：JSON 序列化 float 可能有末位差异。玩家 transform 受此影响，但复活点是神龛而非精确坐标，**无玩法影响**。

**被否方案与理由**

| 方案 | 否决理由 |
|---|---|
| **B. ConfigFile** | 对嵌套结构（`islands_unlocked` 数组、技能列表）表达力差，需要扁平化成 `section/key` 或塞入序列化字符串，反而更难维护与迁移。 |
| **C. 二进制 `store_var`** | 不可读，调试灾难；且 `var_to_bytes` 的格式与引擎版本耦合——**Godot 升级可能导致老存档无法读取**，与 ADR-001 的版本升级策略直接冲突。 |
| **D. ResourceSaver `.tres`/`.res`** | 危险：`.res` 反序列化会实例化脚本/资源，**存在从恶意存档加载执行代码的风险**（`load()` 任意资源路径）；且资源格式随引擎演进，跨版本兼容性不保证。 |
| **E. SQLite** | 需引入 GDExtension，违反"零非常规运行时依赖"（`architecture.md` §12.1）。本项目数据量与查询复杂度完全不需要数据库。 |

## 备注

- **与 ADR-002 的强耦合已在决策 3 明确**：任何人想把常量写进存档，都应被本 ADR 与 `tests/unit/test_save_excludes_constants.gd` 拦下。
- **复活不读盘**（`architecture.md` §10.4）：复活是内存态复位 + 传送，不重新加载文件。否则玩家会丢失"上次存档之后的探索进度"，与 GDD S8「保留进度、不掉收集」直接冲突。
- 自动存档：GDD 未要求，v1 **不做**（神龛是唯一存档点是设计意图，自动存档会削弱神龛的意义）。若后续要加，需回 GDD 走变更。
- 待裁决缺口：GDD S8 §⑧「技能点是否可洗点」（即 CONCERN-2 的一半 / 缺口 G4）——schema 已预留 `meta.skill_points` 与 `skills_unlocked` 分离存储，**洗点在数据结构上已可支持**，但 v1 不实现功能。
- 多存档槽：v1 单槽，schema 已预留 `slot` 概念（文件名分离），扩展无需改结构。
