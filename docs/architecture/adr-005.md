# ADR-005 · 移动与物理：`CharacterBody3D` 手动积分 + 自研荡索求解（不用刚体/物理关节）

> 编号 ADR-005 ｜ 日期 2026-08-08 ｜ 作者 程基岩 ｜ 评审 Solo
> 关联：`architecture.md` §3 / §4.1 / §7 ｜ 上游：GDD S2 `movement.md`、S1 `combat.md`、S5 `world-level.md`

## 状态

**已接受（Accepted）**

## 背景

支柱 **P2「垂直即世界」** 要求空中为主玩法场，S2 给出的机制与数值：

- 轻重力 **0.6g（≈ −5.88 m/s²）**；
- **荡 Grapple**：≤15 m 锚点，拉速 12–16 m/s，**动量守恒的摆荡**，空中可连续荡，可脱钩；
- **跃 Leap**：高 3–4 m，顶点 **0.4 s 悬停**，cd 0.6 s；
- **闪 Dash**：水平 4–6 m，兼战斗无敌（10 帧 iframes）；
- 取消链「跃 → 闪 → 斩」连续无断裂，**共享 `CANCEL_WINDOW=8f`**。

边界要求（S2 §⑥）：锚点失效时保留当前速度自然滑落**不瞬移**；越界坠落 0.5 s 后神龛复活；**卡墙 0.2 s 自动解卡**；多锚点重叠取最近且视线无遮挡。

关键张力：**「摆荡」听起来像刚体 + 物理关节的活儿，但 P1 要求它与战斗共享 8 帧取消窗**。一旦交给物理引擎积分，玩家的输入响应就要与求解器的迭代结果博弈——"第 8 帧能否取消"将不再可确定性断言，ADR-003 的整数帧计时会在移动动词上失效。

Godot 4.6 起 Jolt 已是 3D 默认物理后端（ADR-001 核验），性能与稳定性都很好——但**用不用刚体模拟角色，与后端是谁无关**。

### 备选方案

- **A. `CharacterBody3D` + 手动速度积分**，荡索为自研约束
- **B. `RigidBody3D` + `Generic6DOFJoint3D` / 弹簧关节**做真实摆荡
- **C. `CharacterBody3D` + 每帧施加"绳约束"后处理**（A 的变体，此即最终形态）
- **D. 全自定义：`PhysicsServer3D` 直接调用，绕过节点**

## 决策

**采用 A/C：`CharacterBody3D` + 手动积分，荡索实现为每 tick 的位置/速度约束投影；不使用 `RigidBody3D`，不使用任何物理关节。**

### 1. 积分模型（全部在 `_physics_process`，即 GDD 的"帧"）

```gdscript
# src/movement/locomotion.gd —— 纯逻辑，可单测
const GRAVITY := -5.88          # 0.6g，来自 GDD S2 §⑤

func integrate(vel: Vector3, state: MoveState) -> Vector3:
    if state.hover_frames_left > 0:      # 跃顶点悬停 0.4s = 24 帧
        state.hover_frames_left -= 1
        vel.y = 0.0
    else:
        vel.y += GRAVITY * DELTA         # DELTA = 1.0/60，常量
    if state.grappling:
        vel = _apply_rope_constraint(vel, state)
    return vel
```

`DELTA` 是**常量 `1.0/60`**，不是 `_physics_process(delta)` 传入的值。因为 tick 率固定（`architecture.md` §3），用常量可保证完全确定性——同样的输入序列在任何机器上产生逐位相同的轨迹，这让"跃→闪→斩 ≤8 帧"这类测试可精确复现。

### 2. 荡索：约束投影而非弹簧关节

每 tick 两步：

```text
1. 若 |pos − anchor| > rope_length：
     把位置投影回球面（沿 anchor→pos 方向），
     并从速度中扣除沿绳方向的分量（保留切向分量）
       → 切向分量保留 = 动量守恒的摆荡（GDD S2 §② 要求）
2. 若玩家按住收绳：rope_length 按 12–16 m/s 缩短（GDD 拉速）
```

这是经典的**位置约束 + 速度投影**（Verlet 风格约束求解），不是弹簧。区别很重要：

- 弹簧关节会**振荡**（绳"弹"）、需要调阻尼、且行为随帧率变化；
- 约束投影**当帧收敛**、无振荡、完全确定，且天然满足"脱钩时保留当前速度自然滑落不瞬移"（S2 §⑥）——脱钩只是停止施加约束，速度原样保留。

### 3. 碰撞用 `move_and_slide()`

`CharacterBody3D.move_and_slide()` 做实际位移与碰撞响应。地形与岛屿用 `StaticBody3D` + 三角网碰撞；锚点用 `Area3D` 做检测（不参与碰撞）。

**卡墙解卡（S2 §⑥ 0.2 s）**：连续 12 帧 `get_slide_collision_count() > 0` 且实际位移 < 阈值 → 沿碰撞法线推离。这是显式逻辑，不依赖物理引擎的穿透恢复。

### 4. 锚点选择（S2 §⑥「最近且视线无遮挡」）

```text
1. Area3D 收集半径 15 m 内候选锚点
2. 按到玩家距离升序
3. 逐个做 raycast 视线检测（碰撞掩码只含地形层）
4. 取第一个通过的；同时用屏幕空间角度加权，偏向准星方向
5. 目标锚点显 RESONANCE_GLOW 描边（stencil，见 architecture.md §6.3）
   不可抓表面显灰（GDD S2 §②）
```

### 5. 与战斗 FSM 的关系

`Dash` / `Grapple` / `Leap` 是 **ADR-003 的同一 FSM 中的状态**，不是独立的移动系统。它们同样通过 `State.is_cancellable()` 参与 8 帧取消窗。移动逻辑（本 ADR）只提供"速度怎么积分"，"何时能切换动词"完全归 FSM 管。

这是 GDD 把 S1/S2 的取消窗口定义为同一常量的工程兑现——**移动与战斗不是两个系统，是同一状态机的不同状态**。

## 后果

**正面**

- **确定性**：固定 `DELTA` + 无刚体求解器 → 轨迹完全可复现，`跃→闪→斩 ≤8 帧`（GDD S2 §⑦）可写成稳定集成测试。
- **手感直接可调**：0.6g、悬停 24 帧、拉速、绳长全是显式数值（存 `.tres`），改完立刻生效，无需与求解器参数博弈。这是 P1/P2 迭代速度的关键。
- **无物理关节的经典病症**：不会有绳索抖动、穿透弹飞、休眠误判、关节爆炸。
- 与 `architecture.md` §3 的物理插值完全兼容：`CharacterBody3D` 受插值自动处理，144 Hz 顺滑。
- 逻辑可抽为纯函数（`src/movement/locomotion.gd`），**无场景树单测**，CI 秒级跑完。
- 越界检测简单：`position.y < world_floor` 即触发复活流程，不依赖物理事件。

**负面 / 成本**

- **自己写物理 = 自己背 bug**。摆荡手感、连续荡的动量传递、极端角度下的约束求解都需要自行调试与保护。**缓解**：约束投影算法本身很短（<50 行）且有成熟公式；已排期 Phase 4 手感 spike 专项验证。
- 失去"免费的真实感"：刚体摆荡在某些边缘情况下会产生自然的意外惊喜，手动积分需要显式设计每种情况。**判定为可接受**——本项目要的是**可控的爽快**，不是模拟真实。
- 与场景中真实刚体物体（可推动的碎石等）交互需要手工处理动量传递。**v1 范围内无此类物体**（GDD 未要求），若后续加入需补充设计。
- 悬停 0.4 s（24 帧）这类"反物理"机制在刚体方案里是 hack，在本方案里是自然的一行——**这反过来证明手动积分才是对的选择**：GDD 的移动设计本身就是非物理的（轻重力、定点悬停、动量守恒摆荡但可随时脱钩）。

**被否方案与理由**

| 方案 | 否决理由 |
|---|---|
| **B. RigidBody3D + 物理关节** | **致命**：求解器迭代结果不可精确预测，破坏 ADR-003 的帧级确定性；"第 8 帧能否取消"变成概率问题，GDD S1/S2 的帧级验收标准无法稳定通过。此外 0.4 s 定点悬停、瞬时 Dash 位移在刚体上都要靠施加巨大冲量或直接改 `linear_velocity`——本质已经绕过了物理引擎，不如不用。 |
| **D. 直接调 PhysicsServer3D** | 绕过节点省下的开销在本项目量级（同屏 ≤12 个角色，`architecture.md` §7.3）完全不重要；却大幅牺牲可读性、可调试性与物理插值的自动支持。过早优化。 |

## 备注

- **Jolt 仍然有用**：虽然角色不用刚体，Jolt 作为 3D 物理后端（4.6 起默认）仍负责碰撞检测、射线查询、Area 重叠——这些正是 `move_and_slide()` 与锚点检测所依赖的，且 Jolt 的查询性能优于旧 GodotPhysics。**不引入 godot-jolt GDExtension**，用引擎内置的即可（ADR-001 §依赖策略）。
- 强依赖 `architecture.md` §3：若固定 60 Hz tick 被推翻（缺口 G2 / RISK-PERF-1），`DELTA` 常量假设需连带重审。
- 待裁决缺口 **G4**：GDD S2 §⑧「是否允许荡中攻击」属 CONCERN-2，MoSCoW 未覆盖。本 ADR 的 FSM 归属方式（Grapple 是 FSM 状态而非独立系统）使得未来支持它只需允许 `Grapple` 挂 `Slash` 子状态——**架构已预留，v1 不实现**。
- **G8 决议（2026-08-08）：实现 lock-on 摄像机；详见 `design/ux/ux-spec.md` lock-on 章节。**
  - **对本 ADR 的影响（Dash 方向解算语义）**：锁定态下 Dash **不采用**纯环形，也**不采用**纯直线，而是在**目标相对极坐标**中解算——纯切向输入退化为定半径圆弧、纯径向输入退化为直线进退、斜向为螺旋。完整理由与实现约束见 **ADR-003 §「G8 附带技术判断」**。
  - **与本 ADR 手动积分方案的契合**：极坐标解算正是"手动逐帧积分"的自然产物——每帧按 `Δradius ∝ radial`、`Δangle ∝ tangential / radius` 推进，闭式、无求解器、整数帧确定性完全保持；若当初选了方案 B（RigidBody3D），实现定半径圆弧需要持续向心力补偿，结果不可精确预测，**再次印证手动积分是正确选择**。
  - **必须守住的不变量**：锁定与未锁定状态下，Dash 的**总位移距离与 `DASH_IFRAMES = 10` 帧完全一致**（弧长 = 直线距离），仅方向语义不同；另需最小半径钳制（建议 1.5 m）以避免半径趋零时角速度发散。
  - 色彩引用：本 ADR 相关表现（受击、危险区）取 `ColorTokens.DAMAGE_WARN=#E5484D`，**不得**误用 `THREAT=#A62C6B`（仅敌/混沌）。取值权威 = **`design/color-tokens.md` v1.0（CONCERN-A 已裁决：color-tokens.md v1.0）**。
- GDD S2 §⑤「锚点密度每 1000 m³ ≥1」与 §⑦「可达比 ≥0.6」由 `tools/` 下的关卡校验工具自动扫描（`architecture.md` §11.2），非运行时逻辑。
