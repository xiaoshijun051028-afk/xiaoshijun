# ADR-003 · 战斗 FSM 实现：节点化状态机 + 整数帧计时

> 编号 ADR-003 ｜ 日期 2026-08-08 ｜ 作者 程基岩 ｜ 评审 Solo
> 关联：`architecture.md` §3 / §4.4 / §4.5 ｜ 上游：GDD S1 `combat.md`、S2 `movement.md`、S4 `enemy-ai.md`、systems-index §2

## 状态

**已接受（Accepted）**

## 背景

S1 要求「idle → {slash, dash, grapple, leap, parry, resonate}」的动词状态机，核心约束来自支柱 **P1「流动即正义」**：

> 斩/闪/荡/跃/格之间必须存在 **≤8 帧**的取消窗口 …… 中断率 < 5% 视为达标。

工程上这带来三个硬要求：

1. **帧精度**：`CANCEL_WINDOW=8f`、`PARRY_WINDOW=6f`、`DASH_IFRAMES=10f` 必须是**可精确断言**的，GDD S1 §⑦ 第一条验收标准就是"测量任意两动词间取消延迟 ≤ 8 帧"。
2. **取消逻辑单点化**：概念文档 §3 明确"6 个动词共用一套取消/预警语言"以防认知过载。若每个动词各写一份取消判定，会漂移成 6 套手感。
3. **玩家与敌人复用**：S4 敌人状态集 `idle/telegraph/attack/recover/stagger/dead` 与玩家结构同构，且 S8 技能树要能把 `CANCEL_WINDOW` 调低到 5 帧（`architecture.md` 中 `CANCEL_WINDOW_MIN=5`）——需要一个统一的读取点。

此外，S1 §⑥ 还要求输入优先级（格 > 闪 > 斩）与 hitstun 上限 0.5 s 防卡死。

### 备选方案

- **A. 节点化 FSM**：`StateMachine` 节点 + 每状态一个子 `Node`
- **B. 枚举 + `match` 巨型 switch**
- **C. 状态资源化**：每状态一个 `Resource`（`.tres`），运行时无节点
- **D. `AnimationTree` / `StateMachine`（AnimationNodeStateMachine）驱动玩法**
- **E. 行为树（Behavior Tree）**
- **F. GDExtension/C++ 自研 FSM**

## 决策

**采用 A（节点化 FSM）作为骨架 + C 的数据外置思想（动词参数放 `.tres`）**，并统一使用**整数帧计时**。

### 1. 结构

```text
StateMachine (Node)          # 持有 current_state、转移裁决、帧推进
├── Idle      (Node, State)
├── Slash     (Node, State)  # 4 段连段由 combo:int 驱动，非 4 个状态
├── SlashHeavy(Node, State)  # 重击蓄力持续态，可中断
├── Dash      (Node, State)
├── Grapple   (Node, State)
├── Leap      (Node, State)
├── Parry     (Node, State)
├── Resonate  (Node, State)
└── Hitstun   (Node, State)  # 上限 30 帧(0.5s) 防卡死
```

选节点而非纯对象的关键理由：**可视化调试**。Godot 远程场景树里能直接看到当前哪个状态节点在跑、检视其导出参数；配合 `DebugOverlay` 显示 `frames_in_state`，调手感时能立刻看出"取消窗到底开在第几帧"。对一个手感靠反复试的项目，这个可观测性直接换算成迭代速度。

### 2. 取消窗单点实现（`architecture.md` §4.4 已给代码）

`State` 基类统一提供 `is_cancellable()`，读取 `GameConstants.CANCEL_WINDOW`；每个状态只声明**自己的取消窗从第几帧开启**（`cancel_open_at_frame`，一个 `@export` 整数）。

- 取消**判定逻辑**只有一份 → 手感不会在 6 个动词间漂移；
- 取消**时机**每个动词可调 → 斩的收招取消点与闪的收招取消点可以不同，这是动作游戏必需的自由度；
- S8 技能树改窗口 → 只改 `GameConstants` 的读取结果，一处生效。

### 3. 整数帧计时（与 `architecture.md` §3 配套）

所有窗口一律 `int` 计数，每物理 tick `-= 1`：

```gdscript
var frames_in_state: int = 0
var iframes_left: int = 0        # 进入 Dash 时 = GameConstants.DASH_IFRAMES (10)
var parry_armed_left: int = 0    # 进入 Parry 时 = GameConstants.PARRY_WINDOW (6)
var hitstun_left: int = 0        # 上限 30 (0.5s)
```

**绝不用 `float` 累加秒数**。因为 §3 已把 1 物理 tick 定义为 GDD 的 1 帧（`physics_ticks_per_second=60`），`DASH_IFRAMES=10` 就是字面 10 次 tick，不存在浮点漂移，也不随显示器刷新率变化。这让 GDD 的验收标准变成**确定性断言**而非概率性观测。

### 4. 转移裁决集中在 StateMachine

`StateMachine.try_transition(intent)` 是唯一转移入口，顺序为：

```text
1. 若 hitstun_left > 0 且 intent 非强制 → 拒绝（GDD S1 §⑥ 硬直期禁输入）
2. 查询 current_state.is_cancellable()
3. 查询目标状态 can_enter()（如 Resonate 需 ResonancePool.can_afford(FINISHER_COST)）
4. current_state.exit() → current_state = next → next.enter()
5. emit EventBus.player_state_entered
```

**输入优先级（格 > 闪 > 斩）不在此处**，而在 `InputManager` 里先裁决成单一意图再送入（`architecture.md` §4.4）。FSM 不该知道"玩家同时按了三个键"，它只处理"玩家想做什么"。

### 5. 动词参数数据化

每个动词一个 `VerbDefinition.tres`（`resources/verbs/`）：帧数、位移距离、伤害区间、cd、取消窗开启帧、命中反馈参数。**代码内禁止玩法数值字面量**（`architecture.md` §11.4 路径作用域规则）。手感调整 = 改 `.tres`，不重新编译、不改代码、可由非程序员调。

### 6. 敌人复用同一套

S4 敌人用同一 `StateMachine` + `State` 基类，状态集换成 `Idle/Telegraph/Attack/Recover/Stagger/Dead`，差异全在 `EnemyDefinition.tres`。`telegraph_frames` 以帧存储（Normal 36–72 帧 = 0.6–1.2s；Hard 24–48 帧 = 0.4–0.8s），与帧基准统一。

这直接让 CONCERN-1（Hard telegraph 下限 0.4s 待 A/B）**成为纯数据实验**：Phase 4 调参改 `.tres` 即可，不动一行代码。

## 后果

**正面**

- GDD S1 §⑦ / S2 §⑦ 的帧级验收标准可写成确定性集成测试（gdUnit4 `SceneRunner.simulate_frames()` 逐帧推进，见 `architecture.md` §11.1），且**不会 flaky**。
- 取消手感单点可调，改一个常量全局生效——支撑 P1 的快速迭代。
- 玩家/敌人共用基类，S4 实现成本大幅下降；新增敌人原型 = 新增一个 `.tres` + 可能少量特有状态。
- 状态节点在远程场景树可见，调试成本低。
- 与 ADR-002 协作干净：`Resonate.can_enter()` 调 `ResonancePool.can_afford()`，池不足则转移被拒 → 自动满足 GDD S1 §⑥「共鸣不足灰显、不进入共鸣态」。

**负面 / 成本**

- 每个状态一个节点，玩家场景节点数增加（8 个）。实测开销可忽略（状态节点无 `_process`，只被 `StateMachine` 主动调用）。
- 节点化 FSM 的状态间共享数据要走 `StateMachine` 或宿主，比单一 `match` 块略啰嗦。
- **状态爆炸风险**：若后续加"荡中攻击"（CONCERN-2 / 缺口 G4），会出现状态组合问题。**已预留**：`Grapple` 状态支持挂子状态（sub-state），但**v1 不实现**，维持 MoSCoW 未覆盖的判定。

**被否方案与理由**

| 方案 | 否决理由 |
|---|---|
| **B. 枚举 + 巨型 match** | 6 动词 × 取消窗 × 连段 × 硬直的组合会让单个函数膨胀到不可读；取消逻辑必然被复制多份，违反"共用一套取消语言"。 |
| **C. 纯状态资源（无节点）** | 失去远程场景树可视化，调手感时看不见当前状态；且 `Resource` 在编辑器中修改有写回磁盘风险（同 ADR-002 对 D 的分析）。**但其数据外置思想被采纳**（动词参数用 `.tres`）。 |
| **D. AnimationTree 驱动玩法** | 致命：动画状态机以**秒**和混合权重工作，无法表达"第 8 帧精确开窗"；且把玩法逻辑绑死在动画资产上，美术改动画会破坏手感。**正确用法**：AnimationTree 由玩法 FSM 单向驱动（玩法是主、动画是从），不反过来。 |
| **E. 行为树** | BT 擅长"AI 做什么决策"，不擅长"精确到帧的输入响应窗口"。玩家角色不需要决策，需要确定性响应。**敌人 AI 若后期决策复杂化，可在 `Idle` 状态内嵌 BT 做目标选择**，但状态层仍是 FSM。 |
| **F. GDExtension/C++ FSM** | 过早优化。FSM 每帧成本在微秒级，玩法逻辑总预算 4 ms（`architecture.md` §7.2）绰绰有余。引入 C++ 会拖慢迭代（每次改都要编译），与 P1 的迭代需求直接冲突。 |

## 备注

- **强依赖 `architecture.md` §3 的时间基准决策**。若 §3 的固定 60 Hz tick 因输入延迟问题被推翻（风险 RISK-PERF-1 / 缺口 G2），本 ADR 的整数帧计时需连带重审——届时所有帧常量需重新换算，是一次高成本变更。这是 Phase 4 首个 spike 必须优先验证 §3 的原因。
- 动画与 FSM 的对接：FSM 进入状态时通过 `AnimationTree` 的 `travel()` 请求动画，**但不等待动画**。玩法帧数由 `.tres` 定义，动画只是表现；动画比玩法长/短由美术侧调整以匹配，不允许反向修改玩法帧数。
- 色彩引用：本 ADR 涉及的状态可视化（取消窗提示、无敌帧闪烁等）一律取自 `ColorTokens`，取值权威 = **`design/color-tokens.md` v1.0（CONCERN-A 已裁决：color-tokens.md v1.0）**。注意 `DAMAGE_WARN=#E5484D` 用于受击/低血，**不得**误用 `THREAT=#A62C6B`（仅敌/混沌）。

- **G8 决议（2026-08-08）：实现 lock-on 摄像机；详见 `design/ux/ux-spec.md` lock-on 章节。** `CameraRig` 自始设计目标锁定层，Dash/Grapple 方向解算按下节的极坐标解实现。

### G8 附带技术判断 · 锁定态下 Dash 的方向解算（程基岩，2026-08-08）

**结论：都不是。既不做"纯环形"，也不做"纯直线"，而是在【目标相对极坐标】中解算——侧向输入退化为环形、前后输入退化为直线、斜向输入为螺旋。**

**理由一：基底必须是目标相对，而非相机相对（确定性要求）。** 锁定期间相机存在跟随/回中插值（`CameraRig` 在 `_process`，见 `architecture.md` §3），若用相机基底解算 Dash 方向，则同一时刻同一摇杆输入会因相机插值进度不同而得到不同世界方向——**这直接违反本 ADR 的帧级确定性**，也会让"第 8 帧取消接闪"这类连段在录像回放中不可复现。目标相对基底（`target.pos - player.pos` 定义径向轴，其与 up 的叉积定义切向轴）是稳定量，与相机动画状态解耦。锁定时相机本就朝向目标，两套基底近乎重合，因此**改用目标相对不会与玩家直觉冲突**——这正是 lock-on 让方向语义变清晰的原因。

**理由二：纯环形在前后输入上是错的。** 后拉摇杆的玩家意图是"拉开距离/脱战"，前推是"贴脸/进攻"。若一律环绕，前后输入将无法改变半径，玩家失去距离控制权——这在需要拉开安全距离读招的 Boss 战里是致命的手感缺陷。

**理由三：纯直线在侧向输入上是错的，且代价被低估。** 侧向 Dash 的用途是"绕开预警扇形并保持在自己的攻击距离上"。直线侧闪会同时改变与目标的距离，落地后半径变了：(a) 可能滑出自己的攻击范围，让 dodge→punish 的固定节奏失效；(b) 可能滑进 AoE 边缘；(c) 相机为重新居中目标必须补一段 yaw 旋转，**恰好发生在 `DASH_IFRAMES=10f`（约 167 ms）这个玩家最需要读招的窗口内**，画面摇摆直接损害可读性。极坐标解保持半径不变，落地后间距一致 → **dodge 后的反击时机可学习、可肌肉记忆**，这正是"爽快"手感的工程基础。

**理由四：极坐标解连续，不需要阈值判定。** 把摇杆输入在目标相对基底下分解为径向分量 `r̂` 与切向分量 `t̂`，Dash 位移在极坐标中按 `Δradius ∝ radial`、`Δangle ∝ tangential / radius` 积分。纯切向 → 定半径圆弧；纯径向 → 直线进退；斜向 → 螺旋（边绕边贴，正是斜推摇杆的自然预期）。**若改用"侧向走环形/前后走直线"的离散分支，会在 45° 附近出现抖动翻转**，需要迟滞补丁；极坐标解天然连续，无此问题。

**实现约束（写进 Story 验收）**
1. **总位移距离与 `DASH_IFRAMES=10f` 不随锁定状态改变**——弧长 = 直线距离，保证平衡与 i-frame 覆盖率不因锁定而漂移。
2. **最小半径钳制**（建议 1.5 m）：半径趋零时角速度发散，低于阈值退化为纯直线。
3. **最大半径/脱锁距离外**直接走直线（此时弧≈直线，省算力且避免大扫掠）。
4. **逐帧解析积分**，禁止物理求解器介入（承 ADR-005 手动积分），保证整数帧确定性。
5. 弧线路径仍走 `move_and_slide()` 逐帧推进，**不做路径预测式避障**；多敌场景下环绕撞到第二个敌人属预期行为，不自动修正。
6. **未锁定时**：一律相机相对直线，仅方向语义不同，距离/帧数完全一致。
